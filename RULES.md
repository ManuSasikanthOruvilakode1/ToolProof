# Project Rules

These rules apply to every file, commit, run and result in ToolProof. Sections A, B and I match the
rules used across the other portfolio projects; the other sections are specific to this project.

A rule changes only after a `DECISION` entry in [PROCESS_LOG.md](PROCESS_LOG.md) that says which
rule changed and why.

---

## A. Content rules

1. **No personal information.** Do not include any personal names, email addresses, phone numbers, student IDs, or any other personally identifiable information (PII) in any project file. This includes people who help validate tasks: refer to them as `rater_a`, `rater_b` and so on.

2. **No university details.** Do not reference any university names, course codes, assignment numbers, unit outlines, lecturer names, or any other university-specific information.

3. **No AI watermarks.** Do not include any ChatGPT, Claude, Copilot, or other AI-tool watermarks, signatures, disclaimers, or auto-generated attribution lines (e.g. *"Generated by ChatGPT"*, *"Created with Claude"*).

4. **No assignment context.** This is a standalone portfolio project. Do not frame it as coursework, homework, or an academic submission.

---

## B. Code and documentation standards

5. **Original naming.** Use meaningful, descriptive variable, function and file names that reflect the project's purpose.

6. **Clean commit history.** Commit messages describe *what* changed and *why*, and do not reference any AI tool. Format: `<area>: <what> (<task ID>)`, e.g. `env: add issue_refund policy limits (P2.6)`. Areas: `env`, `agent`, `bench`, `eval`, `runner`, `app`, `ci`, `docs`, `log`, `chore`.

7. **Reproducibility.** The project uses `pyproject.toml` with a committed `uv.lock`, and also exports a `requirements.txt` (`uv export --no-hashes > requirements.txt`) for people who do not use uv. The README has setup instructions that work from a clean clone.

8. **Evaluation honesty.** All reported metrics come from actual runs on held-out data. Do not fabricate results or inflate numbers. (Section C expands this rule.)

9. **Quality gates.** Code is merged only when ruff, mypy and pytest pass. New tools, checkers and statistics functions come with tests in the same commit.

10. **No secrets in the repository.** API keys live in environment variables or an untracked `.env`. Traces and manifests must never contain keys or request headers.

---

## C. Evaluation integrity

11. **Dev is for tuning; test is for reporting.** Prompts, strategies, tool descriptions, step limits and gate thresholds are tuned on the **dev** split only.

12. **The test set is locked.** After P4.9, test tasks are covered by `tasks/test.lock`. Changing a test task requires a `DECISION` log entry, a `BENCHMARK_VERSION` bump and a new lock. Never regenerate the lock just to make a check pass.

13. **Test runs are registered.** Every start, resume and completion of a test-split run is appended to `results/test_run_register.jsonl`. Test runs need `--confirm-test-run`. A test run that is thrown away is still reported in the register and the log, with the reason.

14. **Freeze before testing.** Experiment configs and prompts are frozen (hashes logged, tag `experiments-frozen`) before the first test run of P6.4.

15. **Every number has an interval.** Success rates, pass^k and process metrics are reported with 95% CIs (task-level bootstrap). Comparisons are paired, with Holm correction inside each experiment.

16. **Rule-based primary scoring.** The primary metric comes only from rule-based checkers. An LLM judge may appear only as a clearly labelled secondary metric, with its agreement against manual labels reported.

17. **Report what happened.** Negative, null and surprising results are reported. Excluded models, runs or tasks are listed with the reason.

18. **No mixed runs.** One run equals one config, one benchmark version, one model digest and one prompt version. Resume refuses on any mismatch; start a new run instead.

19. **Every README number is reproducible** by `scripts/reproduce.sh` from committed configs, tasks and code.

---

## D. Sandbox safety

20. **No `eval` or `exec`** anywhere in tool code. The calculator uses a whitelisted AST evaluator.

21. **No network access from tools.** `send_email` writes to the `outbox` table only. Distractor tools return generated data. Tests check that no tool imports a networking library.

22. **Read-only SQL.** `sql_query` uses a read-only connection, one statement per call, a row cap and a time limit.

23. **Isolated state.** Every trial gets a fresh copy of the world database. Tools may only read and write inside the project's `data/` directory and the trial's temporary directory.

24. **Determinism.** Tools use the frozen clock and seeded randomness only. Fault injection is seeded and recorded in traces.

---

## E. Benchmark authoring

25. **Every task has an oracle** that passes all of its checkers (`toolproof bench oracle`). A task without a passing oracle is not part of the benchmark.

26. **Checks are verifiable.** Each task checks the answer, the final world state, or both. Write and policy tasks must check the final state, not just the text of the answer.

27. **No hints for the agent.** Task prompts read like real user requests. They do not name tools or describe the solution steps unless that is the point of the task.

28. **Unique and versioned.** Task IDs are unique and never reused. Any change to a task bumps its `version` field.

29. **Distractor tools are never required** by any task's oracle.

---

## F. Process log (`PROCESS_LOG.md`)

30. **Append-only.** New entries go at the **end** of the file. Existing entries, including their wording, typos and formatting, are **never edited, reordered or deleted**.

31. **Corrections are new entries.** To fix a wrong entry, append a `CORRECTION` entry that references it (`--ref LOG-00NN`) and gives the correct information.

32. **Issues are closed by new entries.** An `ISSUE` stays open until a `RESOLVED` entry references it.

33. **Use the helper.** Prefer `python scripts/devlog.py add ...`, which assigns the next ID, timestamps the entry, appends it and re-seals the log. Manual appends are allowed if they follow the entry format; run `python scripts/devlog.py seal` afterwards.

34. **Verify integrity.** `python scripts/devlog.py verify` runs in pre-commit, in CI and at the start of every recovery. If it fails, follow the log-integrity step in [CHECKPOINT.md](CHECKPOINT.md) and never "fix" it by sealing over the change.

35. **When to log** (at minimum):

    | Event | Entry type |
    |---|---|
    | A task ID is completed | `DONE` |
    | Files are added, changed or deleted in a meaningful way | `EDIT` |
    | A scope, design, rule or plan choice is made | `DECISION` |
    | Something is learned from data, a run, a test or a review | `FINDING` |
    | A problem, bug, blocker or open question appears | `ISSUE` |
    | An issue is fixed or answered | `RESOLVED` |
    | An experiment run starts, finishes, is resumed or is discarded | `EXPERIMENT` |
    | A checkpoint is saved | `CHECKPOINT` |
    | Recovery mode is run | `RECOVERY` |
    | An earlier entry was wrong | `CORRECTION` |
    | Anything else worth keeping (ideas for v2, links, reminders) | `NOTE` |

36. **Be specific.** Entries name task IDs, files, commands, run IDs and numbers. "Fixed stuff" is not an entry.

37. **Log content follows section A.** No names, emails or other PII in the log.

---

## G. Checkpoints and recovery

38. **Save a checkpoint** (procedure in [CHECKPOINT.md](CHECKPOINT.md)):
    - at the end of every work session;
    - after finishing every task ID that changes code or data;
    - before risky operations: large refactors, dependency upgrades, deleting files, test-split runs, changing the test lock;
    - after about 90 minutes of continuous work;
    - when blocked, before switching to something else.

39. **Only the current-checkpoint block is replaced.** The protocol text in `CHECKPOINT.md` stays. Every save also appends a `CHECKPOINT` entry to the log, so the history of checkpoints is never lost.

40. **Start every session in recovery mode** (light mode at least; full mode after a crash, after a gap of 7 days or more, or when the repository looks different from the checkpoint).

41. **The log wins over the checkpoint** if they disagree and the log entries are newer. Update the checkpoint to match and record a `RECOVERY` entry.

42. **Checkpoint commits are tagged** `checkpoint/CP-NNNN` so any save point can be restored.

---

## H. Git workflow

43. `main` always passes CI. Work happens on branches named `p<phase>/<task-id>-<short-name>`, e.g. `p2/p2.6-refund-tool`.

44. Work-in-progress commits at a checkpoint are allowed on branches, with the `wip:` prefix; squash them before merging into `main`.

45. Never commit `results/runs/` (large and regenerable), `.env`, model files or caches. Published summary results are committed under `reports/`.

46. Never rewrite history on `main`, and never force-push tags.

---
